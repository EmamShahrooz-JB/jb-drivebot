# تست‌ها: چه چیزی اثبات می‌شود و چه چیزی نه

```bash
npm test                 # همه
npm run test:unit        # بدون I/O سنگین
npm run test:integration # سرورهای واقعی محلی + SQLite واقعی
npm run typecheck
npm run smoke            # بوت واقعی سیستم
```

## اصل حاکم

هیچ تستی منطق خودِ ما را mock نمی‌کند. آنچه mock می‌شود فقط **سرویس‌های بیرونی** است (Drive/Google) که برای تست به آن‌ها دسترسی نداریم؛ جای آن‌ها با سرور HTTP محلی و واقعی شبیه‌سازی می‌شود که همان پروتکل را صحبت می‌کند.

| نوع mock | جایگزین واقعی | چرا قابل قبول است |
|---|---|---|
| Drive API | `tests/helpers/fake-drive.ts` — سرور HTTP واقعی که `POST /upload/drive/v3/files` → `308` → `PUT /session/:id` → `200` را پیاده می‌کند | پروتکل Resumable در سمت **کلاینت ما** واقعی تست می‌شود |
| Google OAuth | سرور HTTP محلی که endpoint توکن را شبیه‌سازی می‌کند | PKCE/State/ساخت URL/ذخیره‌سازی همه واقعی هستند |
| تلگرام | فراخوانی مستقیم توابع (`transferToDrive`, `handleCallback`) بدون Bot API | منطق کسب‌وکار تست می‌شود؛ UI فقط wiring است |

## آنچه واقعاً تست شده

- **رمزنگاری**: seal/open، جداسازی purpose، رد دستکاری ciphertext، رد AAD اشتباه، Signer (انقضا/جعل/کلید دیگر).
- **SSRF**: ۲۵+ حالت IP، متادیتای ابری، DNS rebinding، پین‌کردن آدرس در `guardedLookup`، بلوک شدن در `NODE_ENV=production` حتی با `allowLoopback`.
- **OAuth کامل**: `prepare` → URL با PKCE/state/offline → callback → تبادل روی سرور → ذخیره رمزنگاری‌شده → مصرف یک‌بارمصرف → رد State اشتباه → رد redirect غیر-loopback.
- **Drive Resumable**: تک‌chunk، چند‌chunk، قطع وسط آپلود و **ازسرگیری از offset**، خطای 503 به‌صورت retryable، Abort، تطابق اندازه فایل، ساخت/یافتن پوشه.
- **دانلود**: محتوای دقیق، MD5، بدون content-length، زنجیره Redirect، Redirect به متادیتا (بلاک)، حلقه Redirect، صفحه HTML، سقف حجم، 5xx.
- **صف**: اجرا، هم‌زمانی per-type، اولویت، retry با backoff و موفقیت، عدم retry برای خطای غیرگذرا، لغو حین اجرا، بازیابی orphan، job بدون handler.
- **دیتابیس**: مهاجرت idempotent، تطابق فایل‌های SQL با کد، همه ریپازیتوری‌ها، dedupe، آمار روز/ماه، تنظیمات خراب، کد جفت‌سازی یک‌بارمصرف.
- **ZIP**: ساخت/فهرست/استخراج، `../`، مسیر مطلق، symlink، Zip Bomb واقعی (۲۰MB صفر → چند KB)، سقف تعداد و حجم، لغو.
- **خط لوله آپلود**: ساخت پوشه ریشه، نمایش مسیر دسته‌بندی، dedupe با هش، مقصد دستی، نام مخرب، همه حالت‌های پوشه‌بندی، آمار.
- **نقطه ورود production** (`src/index.ts` اجرای واقعی با `tsx`): بوت کامل با Bot API شبیه‌سازی‌شده، بالا آمدن HTTP روی `0.0.0.0:PORT`، پاسخ `/health` و `/`، رد مسیر ناشناخته و کد جفت‌سازی نامعتبر، **عدم حضور توکن در لاگ**، و خاموشی تمیز با `SIGTERM` (exit code 0).

## آنچه تست نشده (صادقانه)

۱. **تماس واقعی با Google Drive/API**: نیاز به Client ID/Secret و حساب شما دارد. مسیر کد واقعی است، ولی اولین تماس واقعی شماست.
۲. **Bot API واقعی تلگرام**: تست‌های بوت، Bot API را با سرور stub صدا می‌زنند (getMe/getUpdates). یعنی مسیر polling و wiring واقعی تست شده، اما ارسال/دریافت واقعی فایل و کلیک واقعی روی دکمه‌ها در کلاینت تلگرام آزمایش نشده است.
۳. **درایور Postgres**: کد نوشته و typecheck شده، اما Postgres در این محیط نبود؛ فقط SQLite یکپارچه تست شده. کوئری‌ها با یک اسکیمای مشترک نوشته شده‌اند تا ریسک کم شود، ولی **قبل از استفاده production یک‌بار `npm run migrate` و یک آپلود روی Postgres اجرا کنید**.
۴. **حالت `local-exchange`**: کد و سازگاری رمزنگاری تست شده (تست `pairing-compat`)، اما جریان کامل end-to-end فقط برای `server-exchange` اجرا شده است.
۵. **yt-dlp**: پیش‌فرض خاموش؛ در این محیط باینری نبود. کد به‌صورت `spawn` با آرگومان‌های امن نوشته شده ولی اجرای واقعی دانلود ویدیو آزمایش نشده.
۶. **حجم‌های بزرگ واقعی**: تست‌ها با فایل‌های تا چند MB و chunk ۲۵۶KB کار می‌کنند. رفتار چند‌گیگابایتی (Disk/Network) در محیط شما اندازه‌گیری نشده.
۷. **Webhook mode**: کد نوشته شده (mount روی همان پورت + secret)، اما با تلگرام واقعی ثبت و تست نشده. Long Polling مسیر پیش‌فرض و ساده‌تر است.
۸. **Local Bot API Server**: کد از `TELEGRAM_API_ROOT` پشتیبانی می‌کند، اما سرور واقعی در این محیط اجرا نشده.
۹. **UI تلگرام**: پیام‌ها/دکمه‌ها به‌صورت واحد (views/keyboards) ساخته شده‌اند، اما هیچ‌کدام با کلاینت واقعی تلگرام کلیک‌نشده‌اند.
